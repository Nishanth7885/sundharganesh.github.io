Centralized Source Code Management using Gitea

Migrated internal projects from local folders to a self hosted Git platform with proper version control, traceability, and access control.

Gitea Git Linux Ubuntu

Executive Summary

From Local Folders to a Single Source of Truth

G. Kuppuswamy Naidu Memorial Hospital, 2026

Source code for internal applications used to live in scattered project folders on developer laptops and shared drives. There was no single source of truth, no review trail, and no way to recover work if a machine went down. I deployed and configured a self hosted Gitea server to fix this, then migrated existing projects onto it and trained teams on basic Git workflows.

Self hosted Gitea in production
Repos migrated from local folders
Full commit history and traceability

The Problem

Without a central Git server, every team handled source code their own way. Some used a project folder on a shared drive, some kept code only on the developer machine. There was no concept of branches, pull requests, or code review built into the workflow.

  • No single source of truth for any internal codebase.
  • No history of who changed what or why.
  • Onboarding a new developer meant copying a folder.
  • If a laptop died, work could be lost.
  • No platform to plug into for any future CI/CD work.

What I Built

1. Deployed and hardened Gitea on Linux

Stood up Gitea on an Ubuntu server with a dedicated service account, systemd unit, and regular backups of the data directory and database. Gitea was the right fit for the hospital because it is lightweight, self hosted, and stays inside the network.

2. Created organizations and teams

Modeled the actual team structure inside Gitea so each application area has its own organization and the right people have the right access. No more shared logins or anonymous folder shares.

3. Migrated existing projects

For each active internal project, initialized a repository, imported the current code, and got the original developer to make their next change as a Git commit instead of editing the shared folder. Once the new workflow stuck, the shared folder was decommissioned.

4. Trained teams on Git basics

Most developers had never used Git in a structured way. Ran short, practical sessions on clone, branch, commit, push, pull request, and merge. Wrote a short internal cheat sheet so people had something to refer back to.

5. Set the stage for CI/CD

With Gitea in place, the CI/CD project that came next (Jenkins triggered by Git push events) was suddenly possible. This project is the foundation of the whole DevOps modernization at the hospital.

Outcome and Impact

  • Every internal project on the platform has a full commit history.
  • Code is no longer lost when a machine dies or a developer leaves.
  • Reviews happen via pull requests instead of "send me the new files".
  • Provided the platform that the Jenkins CI/CD project hooks into via webhooks.
  • Standardized the way teams collaborate on code across the organization.

What I Learned

  • Tooling without training does not stick. The migration only worked because we taught the workflow at the same time.
  • Self hosted Git is a low cost, high leverage move for a healthcare org with strict data residency.
  • Picking Gitea instead of a heavier platform paid off. Less to operate, faster to run, easier to back up.
