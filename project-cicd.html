CI/CD Pipeline Automation using Gitea and Jenkins

Modernized legacy deployment workflows by introducing self hosted CI/CD with Git push triggers and approval based production gates.

Gitea Jenkins Git Docker Linux Webhooks

Executive Summary

Production CI/CD for a 24/7 Hospital

G. Kuppuswamy Naidu Memorial Hospital, 2026

Internal applications were being deployed manually with copy and paste workflows. The process was slow, error prone, and lacked any audit trail. As DevOps Engineer, I designed and rolled out a self hosted CI/CD platform using Gitea and Jenkins. Git push events now trigger build pipelines automatically. Production deploys still require human approval, so we get speed without losing control.

Faster, repeatable deploys
Approval gated production
Audit trail for every release
Developers trained on Git

The Problem

Before this project, deployments at the hospital looked like this: a developer would build locally, then either an engineer or the developer would copy artifacts onto the server, restart the application, and hope nothing broke. There was no version pinning, no build server, no review step, and no rollback plan beyond "do it again with the old files".

Specifically, the pain points were:

  • Releases sat in one person's head, not in any system.
  • No way to answer "what changed between yesterday and today" with confidence.
  • Rollbacks meant tracking down old binaries on a laptop.
  • Dev teams had no shared workflow, every project ran differently.
  • Production changes happened without a second pair of eyes.

What I Built

1. Self hosted Gitea as the source of truth

Stood up Gitea on a hardened Linux server to give every team a single place to put their code. Project folders that used to live on individual machines became proper repositories with branches, history, and per project access control.

2. Jenkins as the build and deploy engine

Deployed Jenkins on the same infrastructure to handle automation. Each repository got a pipeline that builds, tests where applicable, and ships to a staging environment automatically. Production deploys are a separate, manual approval step inside the same pipeline.

3. Git push triggers via webhooks

Wired Gitea webhooks into Jenkins so that a push to a tracked branch immediately kicks off the right pipeline. Developers do not need to know Jenkins, they just push their code.

4. Approval based production deploys

Production stages in Jenkins require an explicit human click before they run. This keeps speed for dev and staging, but stops anything from landing on production servers without sign off.

5. Developer enablement

Ran working sessions with each dev team on basic Git workflows, branching, pull requests, and how to read a Jenkins build. The platform only works if people actually use it, so this part mattered as much as the wiring.

How It Fits Together

# end to end flow developer commits code | v git push --> Gitea (self hosted, source of truth) | | webhook on push v Jenkins pipeline | +--> build artifact +--> deploy to staging (automatic) +--> wait for approval +--> deploy to production (manual click) | v release recorded in Gitea + Jenkins history

Every step leaves a trail. If a deploy goes sideways, we can see which commit, which build, who approved it, and roll back to the previous green build with the same pipeline.

Outcome and Impact

  • Manual copy and paste deployments are gone for the projects on the new pipeline.
  • Deploy time dropped substantially because the human bottleneck is now just the approval click.
  • Every release has an audit trail tying the commit, the build, the approver, and the timestamp together.
  • Rollbacks became boring. Pick a previous green build and re run the deploy stage.
  • The dev teams are now Git native, which is the foundation for any future automation we layer on top.

This project is the template for how we plan to modernize the rest of the internal application portfolio at the hospital.

What I Learned

  • The hard part of CI/CD in a healthcare org is not the tooling, it is the change management. Most of the win came from training and standardization, not from Jenkins itself.
  • Self hosted tools (Gitea, Jenkins) were the right pick for a network constrained hospital environment. No data leaves the building, and we own every knob.
  • Approval gates are not bureaucracy when they are wired correctly. They are a forcing function for someone to look before production changes.
  • Documentation as you go beats a doc sprint at the end. Every pipeline has a README in its repo.
